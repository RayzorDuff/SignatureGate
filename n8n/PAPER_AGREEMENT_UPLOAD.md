# Protected paper agreement uploads

Paper agreements do not require a Participant email and do not call Documenso. Use deferred Intake, then Participant Functions to select the Participant and assigned Spiritual Practitioner, select an applicable template if available, and upload one signed PDF, PNG or JPEG up to 5 MiB. Multi-page scans should be combined into one PDF. The saved agreement remains pending_review until a Document Reviewer inspects the evidence and supplies a review reason. Upload never grants release eligibility by itself.

## Test deployment sequence

Current provider-specific setup: [Google Drive paper storage](GOOGLE_DRIVE_PAPER_STORAGE.md). The workflow now supports google_drive or nocodb. Update the existing authenticated development workflow in place; do not create a duplicate active webhook. For Drive, configure its OAuth2 credential and private parent folder; the NocoDB-specific instructions below apply only when choosing NocoDB.

1. Apply db/migrations/paper_agreement_upload.sql followed by db/migrations/paper_evidence_storage.sql to signaturegate_test, each twice, then run both paper verification files. The test-only releases/v1.2.0/validate_paper_agreement_test.sh performs those steps with private logs and rollback-only synthetic fixtures. Do not apply this sequence to production or replay all migration files.
2. For a fresh installation import n8n/workflows/SignatureGate - Paper Agreement Upload.json; update an existing development paper workflow in place. The older generic upload workflow/path is retained for existing applications. This new export is inactive and contains credential names without secrets or deployment IDs.
3. On its Webhook node select/create Header Auth credential SIGNATUREGATE_PAPER_UPLOAD. Use a dedicated random secret header, for example X-SignatureGate-Paper-Upload-Key, with a securely generated value. Add the matching header to the server-side N8N datasource in the development Appsmith app; never place its value in action bodies, JS, Git, evidence or returned logs. Other N8N requests can retain their existing configuration.
4. Select the signaturegate_test Postgres credential on both PG nodes. Configure SIGNATUREGATE_EVIDENCE_STORAGE for the reviewed test NocoDB storage destination/credential. NOCODB_BASE_URL must be configured and accessible to the workflow; no production URL fallback is provided. Use an isolated instance or explicitly reviewed test namespace/credential on shared storage. Confirm the normal authenticated retrieval route; files must not become publicly discoverable. Keep actual targets, credentials and mappings private.
5. Save and activate this development workflow. Its webhook uses /webhook/signaturegate/paper-agreements. A webhook-test URL works only while listening; the Appsmith action uses the active webhook route. Save execution payloads remains disabled for successful, failed and manual executions because requests contain document bytes.
6. Pull the companion Appsmith development change, retain the test datasource and use normal development Deploy. Upload one synthetic document for the existing no-email test Participant, inspect/download its evidence, confirm pending_review, then approve it with a Document Reviewer and reason. Do not send a real agreement or change production/master.

The new API action uses appsmith.user.email directly, never a caller-supplied actor parameter. Header authentication protects the service boundary; the workflow separately verifies current canonical account/resource scope, assigned practitioner and active template. Postgres parameters are bound, not interpolated. File type/magic, base64, size and filename checks occur before storage and are repeated by the database reservation API. Only attachment paths returned by storage can reach the completion node. The completion transaction creates one paper agreement, evidence, attribution audit and upload receipt together.

## Uncertain results and recovery

The owner/account-scoped request is saved before dispatch. Check saved paper upload only reads its receipt; ordinary retries never send the file again. A duplicate in-flight workflow invocation cannot claim storage work twice. A completed request returns its existing agreement. Owner/payload and changed-evidence conflicts are rejected.

If the request remains pending, stop and inspect its workflow privately. Resolve pending upload opens a reasoned cancellation dialog. Cancellation records an audited tombstone even if the delayed workflow has not reserved its request yet, preventing both a late first reservation and late completion from creating an agreement. A committed agreement cannot be cancelled through this recovery action. A file already uploaded before a failure/cancellation may be orphaned; identify and clean it up privately after confirming no committed agreement references it. Cancellation deliberately does not delete storage files or rewrite agreements. Select a new file only after resolving the old request.

The database receipt table excludes document bytes. It contains private ownership/resource/request facts, hashes and evidence metadata; review actual invoker grants/backups and retain receipts. A fresh schema/test runner does not validate production owners/grants, storage access or restore/recovery.

## Automatic evidence

scripts/test_paper_upload_workflow.mjs executes the actual workflow Code bodies with synthetic files, validates the authorization/claim branch and binary helper, rejects malformed/type-mismatched/oversized files and unsafe storage responses, and checks disabled execution-payload retention. Backend rollback fixtures cover no-email staff scope, self/unassigned/owner/payload denials, request deduplication, reasoned independent review, cancellation tombstones and completion/audit atomicity. The existing disposable PostgreSQL 16 runner also runs migration reapplication and these paper fixtures before its Intake concurrency cases. Paper-specific simultaneous-session races and live credentials/storage remain separate from those Intake concurrency assertions.
